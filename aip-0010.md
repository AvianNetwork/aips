# AIP-0010: AI Attestation Framework for Avian

```
AIP:     0010
Title:   AI Attestation Framework for Avian
Author:  Avian Network Developers
Status:  Draft
Type:    Standards Track
Created: 2026-05-25
Supersedes: AIP-0004
```

---

## Abstract

This AIP defines a standard framework for AI-generated attestations in the Avian ecosystem.

An AI attestation is a signed, machine-readable report produced by an AI worker, service, or validator about an Avian-related target. Targets may include assets, IPFS CIDs, marketplace listings, addresses, transactions, PSBTs, blocks, mining/network health, software releases, or other ecosystem objects.

This proposal does not introduce AI into Avian consensus. AI attestations are advisory metadata. They may be consumed by wallets, explorers, marketplaces, indexers, monitoring systems, and community tools, but they do not determine whether a transaction or block is valid.

---

## Motivation

Many blockchain projects claim to use AI without defining how AI outputs are produced, verified, versioned, signed, or consumed.

Avian can support real AI-assisted functionality by standardizing attestations that are:

- Signed
- Versioned
- Linked to a specific target
- Linked to a specific model
- Reproducible where possible
- Stored off-chain or anchored on-chain
- Usable by wallets, explorers, and marketplaces

This framework enables AI-assisted use cases such as:

- Asset metadata validation
- IPFS CID health checks
- Duplicate or suspicious content detection
- Marketplace risk scoring
- Wallet and PSBT safety review
- Transaction intent explanation
- Mempool and spam pattern detection
- Network and mining health analysis
- Exchange/service monitoring
- Developer release review

## Specification

### 1. Attestation Object

An AI attestation MUST be represented as a JSON object using a defined schema.

```json
{
  "schema": "avian.ai.attestation.v1",
  "chain": "avian",
  "network": "mainnet",
  "attestation_id": "sha256-or-content-id",
  "target": {
    "type": "asset",
    "identifier": "ASSET_NAME",
    "txid": "optional-transaction-id",
    "vout": 0,
    "cid": "optional-ipfs-cid"
  },
  "model": {
    "model_id": "avian-asset-validator-v1",
    "model_hash": "sha256-model-hash",
    "registry_id": "optional-registry-reference"
  },
  "attestor": {
    "type": "address",
    "address": "AVN_ADDRESS_OR_DERIVED_ID",
    "pubkey": "hex-encoded-public-key"
  },
  "result": {
    "status": "valid",
    "confidence": 0.94,
    "labels": ["metadata-valid", "cid-available"],
    "summary": "CID is reachable and metadata appears valid."
  },
  "evidence": {
    "input_hash": "sha256-input-hash",
    "report_cid": "optional-ipfs-cid",
    "created_at": "2026-06-07T00:00:00Z"
  },
  "signature": {
    "algorithm": "secp256k1",
    "signature": "hex-encoded-signature"
  }
}
```

### 2. Target Types

The following target types are defined in version 1:

```text
asset
cid
marketplace_listing
transaction
psbt
address
block
mempool_event
network_health
release
service
exchange
```

Additional target types MAY be introduced by future AIPs.

### 3. Result Status

The `result.status` field SHOULD use one of the following values:

```text
valid
invalid
warning
suspicious
high_risk
low_risk
unknown
unavailable
inconclusive
```

Consumers MUST treat AI attestations as advisory and SHOULD NOT use them as the sole basis for irreversible user actions.

### 4. Signatures

Each attestation MUST be signed by the attestor.

The signed payload MUST exclude the `signature` field itself.

The canonical signing format SHOULD be deterministic JSON using sorted keys and UTF-8 encoding.

Future AIPs MAY define additional signature schemes, including post-quantum signatures.

### 5. Storage

Attestations MAY be stored in:

- A local indexer database
- IPFS
- Marketplace infrastructure
- Explorer infrastructure
- On-chain anchoring transactions defined by a later AIP

Large reports SHOULD be stored off-chain, with only their hash or CID anchored on-chain.

### 6. Consensus

This AIP introduces no consensus changes.

Avian full nodes are not required to run AI models, validate AI outputs, fetch attestations, or enforce attestation results.

---

## Rationale

AI outputs are probabilistic, model-dependent, and sometimes non-deterministic. Requiring Avian consensus nodes to run AI models would introduce unacceptable complexity and risk.

This AIP therefore standardizes signed AI metadata while preserving deterministic blockchain validation.

---

## Backwards Compatibility

This AIP is fully backwards compatible.

Existing Avian nodes, wallets, assets, and transactions remain valid and unchanged.

---

## Security Considerations

AI attestations may be incorrect, biased, malicious, stale, or produced by compromised models.

Consumers SHOULD display the following information where available:

- Model ID
- Model hash
- Attestor identity
- Confidence score
- Timestamp
- Report source
- Whether multiple attestations agree

Applications SHOULD avoid presenting AI output as absolute truth.

Future AIPs may define:
